# KeyStone AI架构全景图 — 怎么把零件组装成产品

## 先说一个整体概念

整个系统分成三层：

```
第一层：用户界面层（Frontend）
  └── 用户看到的东西：上传按钮、建议展示、追踪面板

第二层：AI大脑层（AI Processing）
  └── 文档解析、匹配计算、建议生成、排序预测

第三层：数据存储层（Database）
  └── 简历、建议历史、申请结果、向量数据
```

```
┌─────────────────────────────────────────────────────────┐
```

## 每个组件的详细说明

### 组件1：文档解析器（Document Parser）

**职责**：把用户上传的文件（PDF/Word/Text）变成结构化数据

**工作流程**：
```
PDF文件 → 文件读取 → 文字提取 → LLM结构化 → JSON输出

JSON输出示例：
{
  "name": "陈大明",
  "email": "dchen@email.com",
  "education": [
    { "school": "NUS", "degree": "Bachelor", "field": "Computer Science", "year": 2020 }
  ],
  "experience": [
    { "company": "ABC Tech", "title": "Software Engineer", "duration": "2020-2023",
      "highlights": ["Built internal tools", "Led team of 4"] }
  ],
  "skills": ["Python", "JavaScript", "Project Management"]
}
```

**技术选型**：
- 文字提取：python-docx（Word）、PyMuPDF（PDF）
- 结构化：Claude Haiku（比Sonnet便宜10倍）
- 成本：约 $0.001/份简历

**注意**：这是唯一一个100%靠LLM的功能，其他功能都可以优化。

---

### 组件2：Job解析器（Job Parser）

**职责**：从URL或文字中提取职位要求

**工作流程（URL模式）**：
```
粘贴URL → 判断平台(MyCareersFuture/JobStreet/LinkedIn)
       → 平台专用爬虫 → 提取HTML
       → LLM结构化 → JSON输出

JSON输出示例：
{
  "job_title": "Senior Software Engineer",
  "company": "DBS Bank",
  "company_type": "GLC",
  "requirements": [
    { "skill": "Python", "level": "required", "weight": 0.8 },
    { "skill": "AWS", "level": "required", "weight": 0.7 },
    { "skill": "Team Leadership", "level": "preferred", "weight": 0.5 }
  ],
  "experience_years": "5+ years",
  "education": "Bachelor's in relevant field"
}
```

**技术选型**：
- 爬虫：Playwright 或 requests + BeautifulSoup
- URL适配器：每种招聘平台写一个专用解析器（MyCareersFuture适配器、JobStreet适配器等）
- 结构化：Claude Haiku
- 成本：约 $0.001/个职位

**注意**：招聘平台可能改版，适配器需要维护。

---

### 组件3：匹配引擎（Matching Engine）

**职责**：计算简历和Job的匹配度

**两种实现方案**：

#### 方案A：纯LLM（现在用）
```
简历JSON + Job JSON → 一起发给Sonnet → "请分析匹配度并解释"

优点：实现简单，立刻能用
缺点：贵（$0.01/次），慢（5-10秒），不一致（不同时间调用结果可能不同）
```

#### 方案B：向量嵌入 + LLM解释（6个月后用）⭐推荐
```
Step 1: 简历 → 嵌入模型 → 向量（1000+维数字）
Step 2: Job → 嵌入模型 → 向量
Step 3: 计算向量相似度 → 匹配分数（0-1）
Step 4: 把分数输给LLM → 生成文字解释

成本：$0.0001/次（便宜100倍）
速度：< 1秒
一致性：相同输入永远相同输出
```

**向量数据库选型**：
- Pinecone（托管，最简单，$70/月 for 100万向量）
- Chroma（开源免费，但需要自己运维）
- Qdrant（开源，更强，但更复杂）

---

### 组件4：建议生成器（Suggestion Generator）

**职责**：逐行生成简历修改建议

**工作流程**：
```
简历每行 → LLM逐行分析 → 建议列表

建议格式：
{
  "original": "负责项目管理",
  "suggestion": "主导跨部门项目组合管理，协调8人团队，交付12个项目",
  "reason": "该职位强调'量化成果'和'团队规模'，你的描述缺乏具体数字",
  "match_aspect": "团队领导和量化成果",
  "confidence": 0.85
}
```

**优化策略（分层调用）**：
```
第一层：Haiku（快 + 便宜）
  → 判断：这行需要修改吗？
  → 如果不需要修改 → 跳过

第二层：Sonnet（慢 + 贵）
  → 只对需要修改的行调用
  → 生成详细建议
```

**成本控制**：
- 每份简历平均10行
- 假设3行需要修改
- 每份简历建议成本：$0.001（Haiku判断） + $0.015（Sonnet生成3条）= $0.016

---

### 组件5：缓存层（Cache）

**职责**：存储中间结果，避免重复调用LLM

**缓存什么**：
```
简历解析结果 → 缓存7天
Job解析结果 → 缓存7天（热门职位可能更长）
匹配结果 → 缓存1天
建议结果 → 缓存（同一简历+同一Job = 相同建议）
```

**技术选型**：
- Redis（内存缓存，速度最快）
- 成本：约 $25/月（AWS ElastiCache）

**命中率的预期**：
- 同一简历分析两次：30%缓存命中
- 同一Job解析两次：50%缓存命中（热门Job被多人查看）
- 整体：减少50-60%的LLM调用

---

### 组件6：预测模型（Predictor）— 6-12个月后

**职责**：预测哪个建议最有效，优先展示

**训练数据来源**：
```
历史数据：
  - 简历A + JobB + 建议X + Outcome → 用户采纳了
  - 简历C + JobD + 建议Y + Outcome → 用户拒绝了

学习：
  - 什么样的简历配什么样的Job，配什么样的建议会被采纳
```

**简化版实现**（不需要训练）：
```
统计法：
  - 统计所有建议的"采纳率"
  - 采纳率 > 70% → 高优先级
  - 采纳率 40-70% → 中优先级
  - 采纳率 < 40% → 低优先级

分类：
  - 按Job类型分组统计
  - "申请GLC职位"的用户，倾向于采纳什么样的建议
```

## 成本汇总（1000月活用户）

| 组件 | 月用量 | 单价 | 月成本 |
|------|--------|------|--------|
| 简历解析（Haiku） | 5,000次 | $0.001 | $5 |
| Job解析（Haiku） | 5,000次 | $0.001 | $5 |
| 匹配引擎（向量） | 5,000次 | $0.0001 | $0.5 |
| 建议生成（Sonnet） | 15,000条 | $0.001 | $15 |
| Redis缓存 | 1个实例 | $25/月 | $25 |
| Pinecone向量数据库 | 100万向量 | $70/月 | $70 |
| PostgreSQL（RDS） | 100GB | $50/月 | $50 |
| **总计** | | | **~$170/月** |

**注意**：这是优化后的成本，缓存命中后不需要重复调用LLM。
未优化的纯LLM方案成本约为 **$3,000-5,000/月**。

## 一个关键决策：自建还是用第三方服务

| 选项 | 适合阶段 | 成本 | 维护成本 |
|------|---------|------|---------|
| 全部用API（Claude、OpenAI） | 现在-6个月 | 中 | 低 |
| 向量数据库自建（Chroma） | 6-12个月 | 低 | 高 |
| 全部用第三方托管 | 任何阶段 | 中-高 | 低 |

**推荐路径**：
- 现在：用API + Redis缓存，专注产品
- 6个月后：加Pinecone向量数据库
- 12个月后：考虑自建部分组件

---

## 架构总结

```
MVP阶段（现在）：
  LLM API（Haiku + Sonnet）+ Redis + PostgreSQL

成长期（6个月）：
  LLM API + 向量数据库（Pinecone）+ Redis + PostgreSQL

规模化（12个月）：
  LLM API + 自建RAG + 预测模型 + 向量数据库 + PostgreSQL
```

**最重要的设计原则**：
1. **数据先行**：数据结构要设计好，LLM调用可以后续优化
2. **缓存为王**：50%的LLM成本可以通过缓存回收
3. **分层调用**：不是所有请求都需要最贵的模型
