# KeyStone的数据需求：AI的燃料

## 一个比喻理解数据和AI的关系

```
数据 = 汽油
AI模型 = 发动机

没有汽油，发动机再贵也跑不动。
汽油不够，发动机只能小功率运转。
汽油够多，发动机才能全功率输出。
```

KeyStone的AI能力上限，由数据积累量决定。

---

## KeyStone需要什么数据（按重要程度分类）

### 第一类：最重要（现在就收集）⭐⭐⭐

#### 1. Suggestion Feedback Data（建议反馈数据）
**含义**：用户看到了什么建议，采纳了哪个，拒绝了哪个

**为什么最重要**：
- 这是训练"好建议"判断模型的核心数据
- 告诉AI："这类简历+这类Job+这类建议 = 用户采纳了"
- 没有这个 → AI建议质量永远停留在"随机猜测好不好"的水平

**记录什么**：
```
{
  suggestion_id: "sug_001",
  user_id: "user_001",
  resume_id: "res_001",
  job_id: "job_001",
  original_line: "负责项目管理",
  suggested_line: "主导跨部门项目组合管理，协调8人团队，交付12个项目",
  was_adopted: true,
  was_modified: false,
  modified_to: null,
  created_at: "2024-04-15T10:30:00Z"
}
```

#### 2. Application Outcome Data（申请结果数据）
**含义**：用户申请了什么职位，结果怎样

**为什么第二重要**：
- 校准AI建议的最终标准
- "我们建议X，用户采纳了，结果用户拿到面试了" → 这条建议可能是好的
- "我们建议Y，用户没采纳，结果用户还是拿到面试了" → Y可能没必要

**记录什么**：
```
{
  application_id: "app_001",
  user_id: "user_001",
  job_id: "job_001",
  resume_id: "res_001",
  applied_at: "2024-04-15T10:00:00Z",
  outcome_stage: "callback_received",  // callback / screening / interview / offer / rejected / no_response
  outcome_at: "2024-04-20T14:00:00Z",
  notes: "Applied via MyCareersFuture"
}
```

---

### 第二类：重要（6个月后开始收集）⭐⭐

#### 3. Resume-Job Match Snapshots（匹配快照）
**含义**：每次分析时，简历和Job的匹配度是多少

**用途**：
- 追踪"用户改完简历后，匹配度有没有提升"
- 验证AI的匹配评估准不准（用户最终拿到面试 = 匹配评估可能准）

**记录什么**：
```
{
  snapshot_id: "snap_001",
  user_id: "user_001",
  resume_id: "res_001",
  job_id: "job_001",
  overall_match_score: 0.73,
  skill_match_details: [
    { skill: "Python", resume_level: "strong", job_level: "required", match: "strong_match" },
    { skill: "Project Management", resume_level: "weak", job_level: "preferred", match: "transferable" }
  ],
  created_at: "2024-04-15T10:30:00Z"
}
```

#### 4. User Behavior Data（用户行为数据）
**含义**：用户怎么和产品互动

**用途**：
- 识别"有效用户"和"流失用户"的行为差异
- 优化产品体验

**记录什么（不涉及隐私）**：
```
{
  event_type: "suggestion_viewed",
  user_id: "user_001",
  suggestion_id: "sug_001",
  time_spent_seconds: 45,
  did_adopt: false,
  did_modify: true,
  created_at: "2024-04-15T10:31:00Z"
}
```

---

### 第三类：有帮助但不紧急（12个月后）⭐

#### 5. Market Benchmark Data（市场基准数据）
**含义**：同类职位的申请者，简历大概是什么水平

**用途**：
- 给用户"你的简历在市场中排前X%"
- 告诉用户"这类职位通常要求Y技能"

#### 6. Employer Response Patterns（雇主响应模式）
**含义**：哪些雇主的回复率高，什么样的简历更容易被捞

**用途**：
- 针对特定雇主的定制建议
- "申请DBS Digital Banking，用这种简历风格回复率高23%"

## 数据增长速度预估

假设：
- 每个用户每月做5次简历分析
- 每次分析产生3条建议
- 每次分析对应1次申请追踪

```
月活跃用户    建议数据      Outcome数据    Resume-Job快照
──────────────────────────────────────────────────────
100          1,500条      500条          100条
1,000        15,000条     5,000条        1,000条
10,000       150,000条    50,000条        10,000条
```

**关键里程碑**：
- 500条 Outcome数据 → 可以做第一版"哪些建议有效"的统计
- 2,000条 Outcome数据 → 可以给B2B客户看方向性结论
- 10,000条 Outcome数据 → 可以训练简单的预测模型
- 50,000条 Outcome数据 → 可以做精准的个性化推荐

## 数据存储成本

按 PostgreSQL 存储（最基础的方案）：

```
500,000条建议记录      →  ~500MB
100,000条申请记录      →  ~100MB
50,000份简历向量       →  ~5GB（每份简历 ~100KB向量）
────────────────────────────────────────
总计                  →  ~6GB → ~$50/月（AWS RDS）

向量数据库（Pinecone等）→ ~$70/月 for 100万向量
```

## 一个重要的设计决策：数据收集的"冷启动"问题

**问题**：
- 产品刚上线，没有数据 → AI建议质量差 → 用户流失 → 更少数据
- 这是一个"鸡生蛋"的问题

**解法（3种，按推荐顺序）**：

### 解法1：用规则过渡（推荐）⭐
在数据不够时，先用规则做建议排序：
- "技能匹配度高的建议排前面"
- "更具体的建议排前面"
- 不依赖历史数据，只是"常识规则"

**优点**：不需要数据，立刻能跑
**缺点**：不能学习，无法个性化

### 解法2：用公开数据做预训练（中期）⭐⭐
在没有自有数据时，用公开数据训练：
- 公开的简历数据集
- 招聘平台的职位要求数据
- 缺点：没有真实的"建议效果"数据

### 解法3：人工标注数据（如果融资后）⭐⭐⭐
如果融资了，可以花钱请人标注：
- 1000份简历 × 10个标注 = 1万元
- 标注："这条建议好不好"
- 缺点：贵，不能 scale

## 数据收集的优先级总结

```
立刻开始（现在）:
├── 建议反馈数据（采纳/拒绝/修改）
└── 申请结果数据（什么职位 → 什么结果）

6个月后开始:
├── Resume-Job匹配快照
└── 用户行为埋点

12个月后开始:
├── 市场基准数据
└── 雇主响应模式
```

**最重要的事**：从第一天开始，就要把"建议反馈"和"申请结果"的数据结构建好。这是产品AI能力的地基。
