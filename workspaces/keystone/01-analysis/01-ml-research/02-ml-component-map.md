# KeyStone AI/ML 模块分解 — 每个功能需要什么"零件"

## 概览：产品的7个AI功能 → 对应的7个AI组件

```
功能层（用户看到）     →    AI组件层（技术实现）    →    数据层（AI需要什么）
─────────────────────────────────────────────────────────────────────────────
简历上传                →    文档解析器              →    无（纯规则）
简历结构提取           →    LLM（Haiku）            →    无（开箱即用）
Job描述提取           →    LLM（Haiku）            →    无（开箱即用）
简历-Job匹配          →    嵌入向量 + 检索系统     →    简历数据库
逐行建议生成           →    LLM（Sonnet）           →    建议历史数据库
建议排序               →    预测模型（未来）        →    Outcome数据
个人基准分析           →    聚类模型（未来）         →    市场数据
```

---

## 模块1：简历解析（现在能解决）

**功能**：用户上传PDF/Word/Text → 提取出结构化数据

**技术方案**：
- 方案A（推荐）：用Claude Haiku做"简历结构化提取"
  - 输入：简历文字内容
  - 输出：JSON格式的结构（姓名、职位、教育经历、工作经历、技能列表）
  - 成本：约 $0.001/份简历
  - 延迟：< 3秒

- 方案B：传统规则解析 + LLM校正
  - 用正则表达式提取大部分内容
  - LLM校正错误部分
  - 成本更低，但准确率也低

**数据需求**：无（LLM本身有知识）

---

## 模块2：Job描述解析（现在能解决）

**功能**：粘贴Job链接或文字 → 提取结构化的职位要求

**技术方案**：
- URL解析（MyCareersFuture、JobStreet等）→ 提取HTML中的关键字段
- LLM从提取的文字中生成结构化的要求列表
- 输出格式：技能列表（硬技能/软技能）、经验要求、学历要求

**数据需求**：无（LLM本身有知识）

**注意**：每种招聘平台的结构不同，需要分别适配（爬虫+解析规则）

---

## 模块3：简历-Job匹配（核心功能，现在是半成品）

**功能**：比较简历和Job要求 → 输出4级匹配评估

**现状问题**：
- 如果只是把简历和Job一起扔给LLM，说"给我做个匹配分析"
- 这在技术上"能用"，但有两个问题：
  1. **贵**：每次匹配都调用一次Sonnet（$0.003-0.015/次）
  2. **不一致**：LLM今天的判断可能和明天不一样（缺乏标准化）

**正确做法（3个月后）**：
```
Step 1: 简历 → 向量化（生成一组数字代表这份简历）
Step 2: Job要求 → 向量化（生成一组数字代表这个职位）
Step 3: 计算相似度 → 输出匹配分数
Step 4: LLM基于分数生成文字解释
```

**技术组件**：嵌入向量模型（Embedding Model）
- 作用：把文字变成一串数字，让计算机能比较"像不像"
- 工具：OpenAI text-embedding-3-small（$0.02/百万tokens）或其他开源方案
- 成本：比纯LLM便宜 50-100倍

**数据需求**：
- 简历语料库（用于校准"相似"的定义）
- 建议历史（什么样的简历匹配什么样的Job效果好）

---

## 模块4：逐行建议生成（核心功能，现在是半成品）

**功能**：简历的每一行 → 生成具体的修改建议

**现状问题**：
- 每次建议都调一次Sonnet
- 成本：$0.01-0.05/条建议
- 一份简历10行 = $0.1-0.5/次分析

**优化方案（6个月后）**：
```
第一层：Haiku（快+便宜）
  - 快速判断：这行是否需要修改
  - 如果不需要 → 跳过，不调用Sonnet

第二层：Sonnet（慢+贵）
  - 只对需要修改的行调用
  - 生成详细建议
```

**更长期的优化（12个月后）**：
```
检索增强生成（RAG）
  - 用户简历这行 → 先从数据库找相似的简历行+对应的建议
  - LLM参考历史建议 + 当前简历 → 生成新建议
  - 效果更好（参考真实案例），成本更低（减少LLM"凭空想"的部分）
```

**数据需求**：
- 建议历史数据库：1000+条"这类简历行 → 这类建议 → 用户采纳了"
- 反馈数据：哪些建议最后被用户采纳了

## 模块5：Outcome Tracking（现在是数据收集，还不是AI）

**功能**：记录用户申请结果 → 追踪回复率

**这是一个数据收集系统，不是AI系统。**

但它是整个产品AI能力的基础：
- 没有Outcome数据 → 无法训练预测模型
- Outcome数据越多 → AI建议越准

**数据结构需求**：
```
申请表：
  - user_id
  - resume_id
  - job_id
  - applied_date
  - stage_reached（Applied → Response → Screening → Interview → Offer）
  - outcome_date
  - outcome（Received_callback / No_response / Rejected / Offer_received）
  - suggestion_ids（用户采纳了哪些建议）

建议表：
  - suggestion_id
  - resume_line_original
  - suggestion_text
  - target_job_id
  - was_adopted（boolean）
  - applied_for_job_outcome（这个建议关联的申请结果）
```

**关键洞察**：这是产品的"数据护城河"。即使竞争对手复制了所有功能，也无法复制这些历史数据。

## 模块6：Suggestion Ranking（未来需要，6-12个月后）

**功能**：用户有10条建议 → 排优先级，先做哪个？

**现在**：LLM随便排
**未来**：基于历史数据学习排序

**技术方案**：
```
训练数据：
  - 简历A + JobB + 建议列表 + 用户最终Outcome
  - 学习："这类简历 + 这类Job + 采纳这个建议 → 通常outcome变好"

预测：
  - 对于新用户：预测每条建议被采纳后对Outcome的影响
  - 排序：按"预期提升幅度"从高到低
```

**数据需求**：至少500+条有完整Outcome的建议记录

---

## 模块7：Personal Benchmark（未来需要，12个月后）

**功能**：用户问"我的简历在申请这类职位的人中算什么水平？"

**技术方案**：
```
聚类分析：
  1. 把所有申请同类职位的简历向量放在一起
  2. 自动分成3-5个群体（顶尖/良好/中等/待改进）
  3. 用户简历落在哪个群体

基准报告：
  - "你的简历在这类职位申请者中排在前30%"
  - "你的弱项是X和Y，这类职位的成功申请者通常有Z"
```

**数据需求**：每类职位至少100+份简历

| 简历-Job匹配 | Sonnet直接做 | $0.01 | $1,000 |
| 建议生成 | Sonnet | $0.02/条 | $2,000 |
| **总计** | | | **~$3,200/月** |

| 简历解析 | Haiku | $0.001 | $100 |

---

## 关键结论

1. **现在**：所有功能都可以用LLM实现，成本可接受（$3-5K/月 for 1000用户）
2. **6个月后**：需要增加缓存层和向量嵌入，成本降70%
3. **12个月后**：需要RAG和预测模型，成本再降30%，同时AI质量大幅提升
4. **所有阶段的核心**：Outcome Tracking数据结构是最重要的基础设施，越早建越好
