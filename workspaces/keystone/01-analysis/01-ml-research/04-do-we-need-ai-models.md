# KeyStone：AI模型调用 vs 自建数据库 — 能否从第一天就摆脱依赖？

## 回答核心问题

**简短回答**：AI模型调用无法完全避免，但可以从第一天起建立"自建数据库"作为AI的"参考书"。这个数据库越大，AI依赖外部模型的程度就越低。

**更长的回答**：这取决于你怎么定义"自建数据库"和"依赖AI"。

---

## 先搞清楚几个概念（用大白话）

### 什么是"RAG"？

**RAG = 检索增强生成**

打个比方：
- **没有RAG的AI**：像一个销售员，凭"经验"随口给建议
- **有RAG的AI**：像一个销售员，先查公司数据库里1000个成功案例，再给建议

RAG不替代AI，它让AI"先查参考书，再给答案"。

---

### 什么是"Bandit"（老虎机算法）？

这是一种"在探索和学习之间找平衡"的算法。

比方说：
- 你有10条建议，不知道哪条最好
- Bandit算法：先随机给用户不同的建议，看哪个效果好
- 学习一段时间后：自动偏向效果好的建议

**Bandit = 自动学习哪个建议更好的算法**

---

### 什么是"SHAP"？

SHAP = 解释AI预测的方法

比方说：
- AI说"这条建议有73%概率被采纳"
- SHAP告诉你"为什么"——是因为这条建议更具体？因为和用户的行业相关？
- **SHAP = AI的"解题步骤"**

## 逐层分析：KeyStone能自建多少？

### 第1层：数据收集（100%可自建，从Day 1开始）✅

**哪些可以完全不依赖AI模型**：
- 用户上传简历 → 存原始文件（AI不参与）
- 用户看到建议，点了"采纳" → 记录这条数据（AI不参与）
- 用户申请了某个职位，有结果了 → 记录（AI不参与）
- 计算"你的回复率是23%" → 统计计算（AI不参与）

**这一层你可以从第一天就完全自建**：
- PostgreSQL数据库
- 用户行为记录表
- 建议采纳/拒绝记录表
- 申请结果记录表

---

### 第2层：规则系统（80%可自建，从Day 1开始）✅

**哪些不需要AI，用规则就能做**：

| 功能 | 规则系统能做到什么 | AI什么时候介入 |
|------|------------------|--------------|
| NRIC检测 | 正则表达式匹配NRIC格式 | 只在不确定时 |
| 简历格式解析 | 检测"教育经历"、"工作经历"等标题位置 | 纠正错误时 |
| Job平台识别 | 检测URL判断是MyCareersFuture还是JobStreet | 适配新平台时 |
| 4级匹配（强/可迁移/可弥补/缺失） | 技能标签匹配（不用AI比较） | 生成详细解释时 |
| 建议采纳率统计 | 纯SQL统计 | 分析原因时 |

**规则系统的限制**：只能处理"明确规则"内的事。
- "Python = Python" → 规则可以匹配
- "项目管理经验"和"PMP认证"是不是同一技能 → 规则很难判断

---

### 第3层：向量数据库 + RAG（可以自建，但需要时间积累）⏳

**这是你们问题的核心——"自建数据库"主要指的是这层**

#### RAG在KeyStone里是什么意思？

```
没有RAG时：
用户简历一行"负责项目管理"
→ 问AI："请给建议"
→ AI凭空想一个建议

有RAG时：
用户简历一行"负责项目管理"
→ 先查数据库："有没有类似的简历行+Job类型+建议历史？"
→ 找到3个相似案例："这类情况，用户通常建议这样改"
→ AI参考这3个案例 + 当前简历 → 生成建议
```

**数据库里有什么**：
- 1000条：简历行 → 建议 → 用户采纳了/拒绝了
- 每条记录标注：Job类型、公司类型、用户行业

**这1000条就是你的"参考书"**

#### 从Day 1能不能建立？

**能建立，但不能立刻使用**。

原因：
- 数据库需要"先有数据"才能检索
- 产品刚上线时数据库是空的
- 需要3-6个月积累第一批数据

**但有一个变通方法——"种子数据"**：
- 不用等用户数据，先用"模拟数据"填充
- 来源：公开简历数据集 + 人工生成建议
- 质量不如真实用户数据，但可以让RAG系统跑起来

---

### 第4层：生成语言、复杂推理（无法自建）❌

**哪些永远需要调用AI模型**：

| 功能 | 为什么无法自建 |
|------|--------------|
| 生成自然的文字建议 | 需要语言模型 |
| 解释"为什么这个建议有效" | 需要语言生成 |
| 处理没见过的简历格式 | 需要语言理解 |
| 多角度分析简历和Job的匹配度 | 需要推理能力 |

**核心限制**：你自己的数据库只能存"过去的案例"，但无法处理"完全没见过的全新情况"。这时必须靠AI模型。

## 能否从第一天就建立"自建数据库"？

**答案：能，但分层**

```
从Day 1就能建（不需要AI参与）：
├── PostgreSQL数据库设计
├── 用户行为记录系统
├── 建议采纳/拒绝追踪表
├── 申请结果记录表
└── 统计计算逻辑（回复率、通过率）

从Day 1就能建（需要AI参与，但不需要依赖AI）：
├── 简历向量数据库（存每一份简历的向量）
├── Job向量数据库（存每一个职位的向量）
├── 相似案例检索系统（用向量相似度匹配）
└── 缓存系统（避免重复调用AI）

需要积累数据后才能真正发挥作用：
├── RAG检索质量（需要1000+条建议反馈）
├── Bandit排序（需要500+条采纳/拒绝记录）
└── 预测模型（需要5000+条完整Outcome）
```

## Bandit和SHAP在KeyStone里的作用

### Bandit（6-12个月后）

**场景**：用户有10条建议，应该先展示哪条？

**Bandit的做法**：
1. 前100个用户：随机展示不同顺序的建议，记录哪个被采纳
2. 学习100个用户后：发现"具体量化"的建议采纳率高23%
3. 之后的用户：把具体量化的建议排前面
4. 同时继续探索：偶尔展示其他类型建议，确保还在学习

**KeyStone的Bandit变体**：
- 不是优化"展示顺序"，而是优化"建议类型"的效果
- 比如："数字+团队规模"类建议在GLC申请中效果好
- "技术栈具体化"类建议在Tech公司申请中效果好

---

### SHAP（12个月后）

**场景**：AI说"这条建议采纳率73%"，用户问"为什么"

**SHAP的解释**：
- 是因为这条建议**更具体**？（贡献度30%）
- 是因为这条建议**匹配Job的关键词**？（贡献度25%）
- 是因为这条建议**和用户行业相关**？（贡献度20%）
- 是因为这条建议**没有过度承诺**？（贡献度25%）

**为什么这对KeyStone重要**：
- B2B客户（大学职业中心）需要向学生解释"系统为什么这样建议"
- SHAP让每条建议都有"AI推理依据"
- 可解释性 = B2B销售的关键卖点

## 关键结论

### 回答你的问题：AI模型调用能否避免？

```
完全避免：不可能
- 语言生成、复杂推理无法用规则替代
- AI模型是"大脑"，数据库是"记忆"

可以大幅减少：可以
- 规则系统处理80%的标准化问题
- 向量检索处理"有先例"的情况
- AI只在"需要创新推理"时才介入

从Day 1就可以自建：
- 数据基础设施（PostgreSQL）
- 缓存层（Redis）
- 向量数据库（Pinecone，存简历向量和Job向量）
- 规则引擎（NRIC检测、格式解析）

从Day 1无法自建（需要数据积累）：
- RAG检索质量（需要先有数据）
- Bandit排序（需要先有行为数据）
- 预测模型（需要先有Outcome数据）
```

### 你的"数据库"具体指什么？

```
如果你指的是"Suggestion Feedback数据库"：
→ 可以从Day 1建立，存用户的采纳/拒绝记录
→ 这是产品最核心的数据资产
→ AI建议质量 = 这个数据库的质量

如果你指的是"向量数据库"：
→ 可以从Day 1建立，存简历和Job的向量
→ 但检索效果取决于数据库里的案例数量

如果你指的是"预测模型"：
→ 不可能从Day 1建立，需要6-12个月数据积累
```

## 建议：Day 1的架构决策

```
第一天就建立的（不用等）：
1. PostgreSQL：存所有用户行为和结果
2. Redis：缓存层，减少重复AI调用
3. 向量数据库（Pinecone）：存简历向量 + Job向量
4. 规则引擎：处理NRIC、格式解析等标准化问题

可以立刻启动，但效果有限的：
5. RAG系统：但数据库是空的，效果有限

需要等待的：
6. Bandit排序（需要100+条行为数据）
7. 预测模型（需要5000+条Outcome数据）
```
