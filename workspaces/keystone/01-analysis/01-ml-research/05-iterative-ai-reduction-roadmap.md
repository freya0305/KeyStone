# KeyStone AI架构完整路线图 — 从Day 1到完全体

## 两个核心目标

1. **从Day 1建立自建数据库** — 能在不依赖AI的地方就不用AI
2. **随迭代减少AI调用** — 数据越多，AI调用越少，成本越低

## 三、每个架构的详细说明

### 架构1：RAG（检索增强生成）— Phase 2激活

**是什么**：让AI生成建议前，先查数据库里的相似案例

**在KeyStone怎么用**：
```
用户简历一行"负责项目管理"
目标Job是DBS银行GLC职位

Step 1: 查数据库
→ "有没有申请GLC职位的简历用过'项目管理'这个描述？"
→ 找到3个相似案例：
  - 案例A：申请GLC + 用了"主导跨部门项目" → 用户采纳了 → 拿到面试
  - 案例B：申请GLC + 用了"管理8人团队" → 用户采纳了 → 拿到面试
  - 案例C：申请Tech公司 + 用了"负责项目" → 用户拒绝了

Step 2: AI参考案例生成
→ "参考案例A和B的建议格式，生成类似但针对当前简历的建议"
→ 输出："主导跨部门项目组合管理，协调X人团队..."

优点：
- 建议更贴合SG市场实际情况
- 减少AI"凭空编造"的情况
- 成本比纯AI生成低70%
```

**数据需求**：1000+条建议反馈记录

---

### 架构2：Bandit（老虎机算法）— Phase 3激活

**是什么**：在"探索新建议"和"用已知好的建议"之间找平衡

**在KeyStone怎么用**：
```
用户有10条建议要排序

Bandit的做法：
- 30%概率：随机排序（探索 — 看看新的建议类型效果如何）
- 70%概率：用已知效果最好的排序（利用 — 不冒险）

学习过程：
Month 1-3: 随机给用户不同建议顺序
→ 发现："量化团队规模"的建议采纳率65%
→ 发现："只说职责不说成果"的建议采纳率20%

Month 4+: 自动把量化类建议排前面
→ 同时保留20%随机排序，持续学习新模式
```

**为什么叫"老虎机"**：
- 老虎机有多个拉杆，每个拉杆胜率不同
- 问题是：应该一直拉胜率最高的那个？还是偶尔试试别的？
- Bandit就是解决这个问题的算法

**数据需求**：500+条建议采纳/拒绝记录

---

### 架构3：A/B Testing（对照实验）— Phase 2激活

**是什么**：同时给用户两种不同建议，看哪个效果更好

**在KeyStone怎么用**：
```
问题："具体量化"的建议 vs "抽象描述"的建议，哪个效果更好？

A/B测试：
- 50%用户看到A版本（具体量化：带领8人团队，交付12个项目）
- 50%用户看到B版本（抽象描述：负责团队管理和项目交付）

数据收集：
- 记录两组用户的建议采纳率
- 记录两组用户的最终Outcome

结论：
→ 具体量化建议的采纳率高23%，但对GLC职位更有效
→ 对SME职位，抽象描述也差不多有效

→ 规则：申请GLC用量化建议，其他职位两种都可以
```

**为什么重要**：
- Bandit是"自动学习"，A/B测试是"主动实验"
- A/B测试结论更可靠，Bandit更快
- 两个配合使用

**数据需求**：100+条行为数据

---

### 架构4：协同过滤（Collaborative Filtering）— Phase 3激活

**是什么**：找"和你相似的用户"，参考他们的选择

**在KeyStone怎么用**：
```
新用户小李：
- 简历：NUS CS毕业，1年经验，有PMP
- 申请：DBS Digital Banking

系统找相似用户：
→ 小张：NUS CS毕业，2年经验，有PMP，申请DBS → 建议A有效
→ 小王：SIM毕业，3年经验，无PMP，申请DBS → 建议B有效

小李更接近小张：
→ 参考小张的建议A
→ 预测：小李用建议A的采纳概率 ≈ 小张的采纳概率（70%）
```

**注意**：协同过滤需要用户量，1000+用户才有效

---

### 架构5：SHAP（模型解释）— Phase 4激活

**是什么**：解释AI的预测，给出每个因素贡献度

**在KeyStone怎么用**：
```
AI预测："这条建议采纳率73%"

SHAP分解：
┌────────────────────────────────────────────────┐
│  基础概率：40%（随便一个建议的平均采纳率）       │
│                                                │
│  +15%  因为这条建议有具体数字（量化效果）        │
│  +10%  因为这条建议匹配Job关键词（项目管理）     │
│  +8%   因为这是GLC职位（历史数据GLC更吃这套）  │
│  -3%   因为建议稍微过长                          │
│  +3%   其他因素                                  │
│  ──────────                                     │
│  = 73%  预测采纳率                              │
└────────────────────────────────────────────────┘
```

**为什么对B2B重要**：
- 职业中心要向学生解释"系统为什么建议你这样改"
- 大学想知道"系统的建议依据是什么"
- 没有SHAP，只能说"AI觉得好"
- 有SHAP，能说"因为你的简历属于X类型，而这类简历在Y情况下建议Z"

---

### 架构6：特征存储（Feature Store）— Phase 3激活

**是什么**：存储"简历特征"和"Job特征"的地方，供机器学习模型使用

**在KeyStone怎么用**：
```
简历特征（每份简历的标签）：
├── skill_vector：[Python, AWS, 项目管理, ...]
├── experience_years：3
├── education_tier：NUS/SMU/NTU/SUTD/SIM/其他
├── has_certification：True（PMP）
├── industry_history：[Tech, Finance, Consulting]
├── quantify_ratio：0.6（60%的描述有具体数字）
└── action_verb_style：led/managed/responsible_for

Job特征（每个职位的标签）：
├── required_skills：[Python, AWS, 项目管理]
├── company_type：GLC/MNC/SME/Startup
├── experience_level：mid/senior
├── education_required：Bachelor/Master
├── leadership_weight：0.7（70%强调领导力）
└── quantify_expectation：0.8（期望具体量化）

这些特征 → 输入机器学习模型 → 预测建议效果
```

**为什么需要单独存储**：
- 训练模型需要大量简历/Job特征
- 如果每次都从原始数据计算，非常慢
- Feature Store = 预计算好，随时可用

---

### 架构7：知识图谱（Knowledge Graph）— Phase 4激活

**是什么**：把"技能"之间的关系建模成图谱

**在KeyStone怎么用**：
```
技能关系图谱：

Python ──相关──▶ Machine Learning
Python ──相关──▶ Data Analysis
Machine Learning ──包含──▶ Deep Learning
PMP ──可替代──▶ Prince2
项目管理 ──相关──▶ 团队管理
NUS CS ──类似──▶ NUS CE
Bachelor ──包含──▶ Bachelor (CS/Finance/...)

应用场景：
用户说"我会项目管理"
→ 知识图谱知道"项目管理 ≈ PMP ≈ Prince2"
→ 匹配Job时，"要求PMP" = "你会项目管理" ✓

用户问"要不要考PMP"
→ 知识图谱知道："申请GLC职位时，有PMP比没有高35%采纳率"
→ 但申请SME时，PMP加成不明显
```

**为什么需要知识图谱**：
- LLM对技能关系的判断不一致
- 知识图谱提供一致、可解释的技能关系
- 对建议生成和匹配都有帮助

---

### 架构8：Learning to Rank（学习排序）— Phase 4激活

**是什么**：比Bandit更高级的排序模型

**Bandit vs Learning to Rank**：
```
Bandit：逐条建议排序
→ "这条建议比那条建议好吗？"（两两比较）

Learning to Rank：整体最优排序
→ "这10条建议的最佳顺序是什么？"（全局优化）
→ 考虑建议之间的相关性、用户疲劳度、Job特点等综合因素
```

**什么时候用Learning to Rank**：
- Bandit处理单个建议的效果
- Learning to Rank处理"一整页建议的展示策略"
- 比如："前3条放高采纳率的，第4-7条放探索性的，第8-10条放补充的"

## 五、每阶段AI调用量减少明细

| 阶段 | AI调用场景 | 调用量 | 成本/用户/月 |
|------|-----------|--------|------------|
| Phase 1 | 简历解析、Job解析、建议生成、匹配解释 | 100%基准 | $3-5 |
| Phase 2 | 简历/Job解析（缓存命中跳过）、建议生成（80%走RAG） | -40-50% | $1.5-2 |
| Phase 3 | Bandit排序（不用AI）、协同过滤（不用AI）、只有生成走AI | -30-40% | $0.8-1 |
| Phase 4 | 预测走模型、解释走SHAP、只有复杂生成走AI | -20-30% | $0.5-0.7 |

**1000用户月度成本演进**：$3-5K → $1.5-2K → $0.8-1K → $0.5-0.7K
