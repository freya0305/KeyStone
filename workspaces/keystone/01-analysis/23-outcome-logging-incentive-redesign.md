# Analysis 23 — Outcome Logging Incentive Redesign

> Phase 01 Analysis — 2026-04-29
> Correction of Analysis 17 — per-application email sequence is wrong for spray-and-pray (海投) users

---

## 问题的根本重新定义

Analysis 17的错误假设：用户投递少量申请，每份申请值得单独跟进。

**现实**：SG典型求职行为是集中海投——
- Fresh grad求职期间投40-120份申请是常态
- PMET转职也可能同时有10-30个pending申请
- 每份申请单独发3封邮件 × 30份申请 = 90封邮件/月 = 垃圾箱

**根本问题**：我们在用"邮件推送"（push）解决一个"主动记录意愿"（pull）问题。

正确框架：不是"催用户记录"，而是"让记录在用户自然回到产品时极低摩擦地完成"。

---

## 用户真实行为模型

### 海投用户（Fresh grad，主要群体）

```
Week 1: 在MCF/JobStreet/LinkedIn投出30份申请
Week 2-3: 等待，同时继续投更多
Week 4+: 开始收到零星回复（3-6%的申请有回应）

记录行为的实际触发点：
✓ 收到一封面试邀请邮件时（情绪高，会主动来KeyStone更新）
✗ 收到"某某公司无消息"提醒邮件（没动力）
✓ 需要再次投一份新工作时（打开KeyStone时顺手更新）
✗ 周日收到"你有30份待更新申请"汇总（太多，放弃）
```

### 精投用户（PMET转职，高价值群体）

```
每月投10-20份，每份都精心准备
更有记录意愿，但也不需要被每份都催
触发点：收到面试邀约后一定会来KeyStone做面试准备
```

## 重新设计的激励策略

### 策略1：下载时顺手记录（保留，最高效）

这不是提醒，是流程的一部分。
```
用户导出优化后的简历
→ "你要把这份简历投给 [公司] 吗？" [是] [不是]
→ 点"是"自动创建申请记录
```
用户此时100%在状态里，摩擦最低。**这是所有方案里最好的记录触发点，不要动它。**

---

### 策略2：回产品时的"批量快速更新"入口（Pull策略，核心）

不等用户想起来，而是**在用户因为其他原因回到KeyStone时，提供一个2分钟的批量更新入口**。

触发场景：
- 用户要分析一份新JD → "开始前，你有5份pending申请，30秒批量更新一下？"
- 用户打开dashboard页 → 顶部banner："你有8份申请等待更新"

**批量更新UX**（关键）：

不是一份份点进去更新，而是类似Tinder的滑动体验：

```
[批量更新 — 30秒完成]

Shopee · Data Analyst           [✓ 收到回复] [✗ 无消息] [—跳过]
GovTech · Software Engineer     [✓ 收到回复] [✗ 无消息] [—跳过]
DBS · Product Manager           [✓ 收到回复] [✗ 无消息] [—跳过]
...

每次3-5秒完成一条
完成后：Streak奖励 "你已记录12份申请 🔥"
```

这是关键设计——**不是per-application, 而是一次性处理所有pending，轻量，甚至有趣。**

---

### 策略3：好消息时的主动回来（情绪触发，高质量记录）

用户收到面试邀请时，**会主动想来KeyStone准备面试**。这是最好的记录时机。

在面试准备入口前加一步：
```
恭喜！你收到了面试邀请
[公司] [职位]

先更新你的申请状态，然后开始准备：
● 状态更新为：[收到回复] ✓
你还有4份申请正在等待 → [一起更新吗？（30秒）]
[开始面试准备 →]
```

**为什么有效**：用户情绪正向，且已经在产品里了，顺手完成记录。

---

### 策略4：游戏化 — 记录率可见奖励

不是惩罚（"你没记录"），而是奖励（"你做得很好"）。

```
你的申请跟踪完整度：72%
━━━━━━━━━━━━░░░░

在top 30%的用户中 ✓

完整记录用户的数据洞察比部分记录用户准确3倍
[继续记录你的申请]
```

**说明这对用户自己有价值**：更完整的记录 → 你自己的统计更准确 → dashboard对你的指导更有价值。不是为KeyStone收集数据，是为你自己建立更好的求职数据。

---

### 策略5：单周汇总邮件（只有一封，且是摘要不是催促）

用Analysis 17的原思路，但根本上改变频率和形式：

```
邮件触发条件：用户本周有≥5份pending申请且上周没有登录
邮件频率：最多每7天一封（无论申请数量）
邮件标题：[姓名]，本周你的求职进展怎么样？
邮件内容：
  你有 [N] 份申请仍在等待中
  其中 [3] 份已超过14天
  [30秒快速更新所有申请 →] ← deep link 到批量更新界面
```

**关键约束**：
- 用户本周已登录 → 不发（已经有机会在产品内更新了）
- 邮件数量：每个账号最多每周1封
- 内容是"你的进展摘要"，而非"你还没更新"的催促

---

### 策略6：阶段性自动关闭（减少噪音，不是靠提醒）

海投用户不可能记住所有没有回音的申请。与其一直push他们更新，不如：

```
30天无任何操作的申请 → 自动标记"无回复（推测）"，移出活跃列表
用户下次登录时显示一个toast：
"已将7份30天未更新申请标记为'无回复' — [查看并更正]"
```

**为什么比持续提醒更好**：
1. 减少pending列表的噪音（用户更愿意维护一个精简的列表）
2. 自动关闭不需要用户动作，减轻负担
3. 给用户撤销/更正的机会（不是强制的）

## 修正后的方案矩阵

| 策略 | 触发方式 | 适用群体 | 预计贡献 | 阶段 |
|-----|---------|---------|---------|-----|
| 下载时记录 | 产品内（导出时）| 全部 | 高 | MVP |
| 批量快速更新 | 产品内（回访时）| 海投用户 | 高 | MVP |
| 面试准备前更新 | 产品内（情绪触发）| 全部 | 中-高 | MVP |
| 游戏化记录奖励 | 产品内 | 全部 | 中 | MVP |
| 单周汇总邮件 | 邮件（每周最多1封）| 沉默用户 | 中 | MVP |
| 自动关闭 | 系统（30天无操作）| 海投用户 | 间接 | MVP |
| Web Push | 浏览器opt-in | Chrome用户 | 低-中 | Phase 2 |
| 邮件解析 | Gmail/Outlook OAuth | 高意愿用户 | 极高 | Phase 3 |

**明确删除**：每份申请独立的Day 3/10/21邮件序列。

## 修正后的日志率预期

| 策略组合 | 预计日志率 |
|---------|---------|
| 仅下载触发（现有）| 8-12% |
| + 产品内批量更新（回访拦截）| 15-20% |
| + 面试准备前更新 | 18-25% |
| + 游戏化 + 单周汇总邮件 | 20-28% |
| + 邮件解析（Phase 3）| 45-60% |

目标MVP日志率：**20-25%**（比原方案15-22%略高，且不会造成邮件地狱）

## 产品设计要求变化

### 新增要求

1. **批量更新UI**：一次性显示所有pending申请，每条有3个quick-action按钮（收到回复/无消息/跳过）。目标：30条申请 < 3分钟完成
2. **回访拦截banner**：用户打开任意页面时，若有≥3条pending申请，显示顶部banner
3. **记录完整度指标**：用户可见自己的跟踪完整度百分比 + 与其他用户对比
4. **自动关闭逻辑**：30天无更新 → 自动标记，下次登录时提示可更正

### 删除要求

1. ~~每份申请的Day 3/10/21邮件序列~~
2. ~~应用级JWT deep links~~（仍保留用于单周汇总邮件，但数量大幅减少）

### 保留

- 单周汇总邮件（每7天最多1封）
- 下载触发记录
- JWT deep links（用于周汇总邮件）
